# Proxmox deployment contract

Run Starfiniti Loyalty in Linux VMs, not privileged containers.

1. Create a Supabase VM with at least 4 vCPU, 8 GB RAM, and 80 GB SSD before production-like tests.
2. Install Docker Engine and Compose. Fetch the official pinned Supabase `self-hosted/v0.8.0` Docker assets, record `.supabase-version` plus the non-secret release-ref/tag-object provenance file, generate fresh secrets, retain Envoy as the default gateway, and set `PGRST_DB_SCHEMAS=public,graphql_public,loyalty`. Before creating or recreating a Supabase service, run `npm run supabase:preflight` with the exact Compose, environment, version, provenance, and bundle-root paths. The preflight hashes every mounted static asset and rejects extra files in sealed source directories; storage and PostgreSQL data directories remain explicitly mutable. The `loyalty` schema is intentionally Data API-visible; explicit grants and RLS remain its authorization boundary. See `docs/operations/SUPABASE_COMPATIBILITY.md`.
3. Put Postgres data on durable storage and configure encrypted off-host PITR/backups. A Proxmox snapshot is supplementary only.
4. Use a separate application VM or isolated Compose project for `compose.app.yml`. Set both image variables to the commit-SHA tags produced by an approved GitHub release (or to their resolved digests), verify the packages are publicly readable, and record the matching plugin checksum before deployment.
5. Terminate TLS at an explicitly managed reverse proxy, expose only 80/443, and restrict Studio to VPN/admin networks.
6. Copy `.env.example` to a secret-managed location outside Git and replace every required placeholder. Set `DASHBOARD_BIND_ADDRESS` to `127.0.0.1` when the reverse proxy shares the application VM, or to the VM's explicit private IPv4 address when a separately firewalled proxy must connect. Never use `0.0.0.0`. Set `SUPABASE_PUBLIC_HOST` to the hostname in `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_INTERNAL_PROXY_IP` to the private address of the TLS reverse proxy. Compose adds that split-DNS mapping only inside the dashboard container, preserving the public HTTPS hostname and certificate while avoiding public-NAT hairpin failures during server-side Auth exchanges. From the matching release source run `npm run deploy:preflight -- --env /absolute/path/to/starfiniti.env`; it validates Compose parity, immutable image selectors, HTTPS origins, explicit binding, the internal proxy mapping, distinct least-privilege database logins, signing-pool structure, optional all-or-none tenant-federation files, and Linux owner-only permissions without printing values.
7. Generate the WooCommerce signing-key pool outside Git with `npm run woocommerce:keys -- --count 20 --output /etc/starfiniti-loyalty/woocommerce-signing-material.json`. The dashboard image runs as UID/GID `1001`; set the pool to owner `1001:1001` and mode `0400` before preflight so the read-only secret mount is usable without granting group/other access. Root can still administer and escrow the file. Each pool reference is consumed by at most one connection. Replenish atomically while retaining existing entries with the same command plus `--append`, restore owner `1001:1001` and mode `0400`, then recreate the dashboard container so its read-only secret mount sees the new inode. Never print or merge key material through shell text processing.
8. Use a dedicated `DATABASE_URL` login that can assume only `loyalty_runtime`; never use a browser, WordPress, or Supabase service credential for ingestion.
9. Use a different `LOYALTY_WORKER_DATABASE_URL` login that can assume only `loyalty_worker`. Run the immutable worker image beside the dashboard; never reuse its credential in the browser-facing service.
10. Transactional SMTP is optional and disabled by default. Configure `LOYALTY_SMTP_HOST`, `LOYALTY_SMTP_PORT`, `LOYALTY_SMTP_SECURITY` (`tls`, `starttls`, or `plaintext`), and `LOYALTY_SMTP_FROM_ADDRESS`, then start Compose with the `smtp` profile. For authenticated SMTP, use an owner-controlled Compose override to mount a root-managed password file read-only into the notification worker and set both `LOYALTY_SMTP_USERNAME` and the container-absolute `LOYALTY_SMTP_PASSWORD_FILE`. Never place the password in the environment file. The notification worker is a separate process, so SMTP failure cannot stop value ingestion, refund, reconciliation, or checkout behavior.
11. Managed Stripe webhook intake, owner billing sessions, and usage dispatch are optional and disabled by default. Leave `LOYALTY_STRIPE_WEBHOOK_SECRET_PATH`, `LOYALTY_STRIPE_API_KEY_PATH`, and `LOYALTY_STRIPE_USAGE_API_KEY_PATH` empty, and do not start the `billing` profile until the sandbox and tenant canary in `docs/operations/STRIPE_BILLING.md` are approved. Empty mounts resolve to `/dev/null`, which both runtimes reject as non-regular secret material. An enabled managed deployment uses separate owner-controlled files for webhook verification, dashboard sessions, and a least-privilege meter-event key. The billing worker receives only the worker database URL and the meter-event key; PostgreSQL authorization must return one dispatch before the worker reads that file or constructs a provider client.
12. Set `DASHBOARD_PUBLIC_ORIGIN` to the canonical HTTPS dashboard origin with no path. Validate health, RLS, auth redirects, guided WooCommerce setup-code import, signatures, effect lease recovery, backup restore, and application rollback in staging before production approval.
13. In the pinned Supabase environment, set `SITE_URL` to the dashboard HTTPS origin, add only required dashboard callback origins to `ADDITIONAL_REDIRECT_URLS`, retain disabled public signup, and create the first Auth user through an approved administration path. Workforce SSO uses the existing Supabase custom provider and does not require dashboard administration credentials. Leave all three tenant-federation paths empty unless that capability is approved; Compose then mounts fail-closed non-files and unrelated dashboard functionality remains deployable. Before enabling tenant federation, also enable `GOTRUE_SECURITY_MANUAL_LINKING_ENABLED`, populate all three distinct owner-only federation files declared in `.env.example`, rerun preflight, and complete `docs/operations/TENANT_FEDERATION.md`. Never place the Authentik API token or Supabase service-role key in the environment file.
14. From the matching release source, follow `docs/operations/INITIAL_TENANT_BOOTSTRAP.md` and run `npm run tenant:bootstrap` with a temporary administration database URL held only in a named environment variable. The atomic deployment-only command creates the initial organization, owner membership, workspace, programme group, link, and immutable audit evidence; browser, dashboard runtime, and worker roles cannot execute it.

## PostgreSQL recovery scripts

Install the reviewed scripts from `scripts/` as root-owned mode `0755` files in `/usr/local/sbin`:

- `starfiniti-postgres-basebackup` is the daily physical-backup command. It stages a `.partial` file, verifies its compression and recovery metadata, publishes it atomically, retains three days of bases, and removes WAL only before the oldest retained base's start segment.
- `starfiniti-postgres-backup-rsync` is the forced SSH command used by the off-host pull identity. It passes the caller's opaque rsync server command to `rrsync -ro` as root and exposes only the completed `base/` and `wal/` tree. Before the restricted wrapper runs, the script requires fixed canonical root-owned non-writable `/usr/bin/rsync` and `/usr/bin/rrsync` files under safe root-owned parent chains, rsync 3.5.0 or newer, and the upstream `--confine-root` integration. It invokes the wrapper under a cleared environment containing only fixed `PATH`, `LC_ALL`, and the opaque original command. The identity cannot run arbitrary commands or write/delete database-VM files.
- `starfiniti-loyalty-postgres-borg-controller` is the only installed Borg controller and accepts exactly one explicit `archive` or `maintain` subcommand. It loads and validates the root-equivalent configuration once and shares numeric state, stable metric publication, and actual repository-identity primitives between both paths. `archive` first requires a canonical non-linked executable owned by root or the service user under safe root/service-owned parent chains and rejects missing, malformed, or pre-3.5 rsync before stage or evidence changes. It then incrementally mirrors completed files with negotiated zstd transport compression into an owner-only systemd state directory and archives that normal file tree with Borg's files cache enabled. The configuration must be an absolute canonical regular non-symlink file inside a service-owned directory that group and others cannot write; every higher ancestor must be service/root-owned and non-writable or sticky-protected. The file must be owned by the effective service user with exact mode `0400` or `0600`. The controller opens it once, validates the opened descriptor, and sources only that descriptor before accepting its required `STARFINITI_POSTGRES_BORG_REPO`; the repository must differ from the whole-VM `BORG_REPO`. Archive mode captures exactly one pure-digit changed-byte/received-byte pair from each completed rsync cycle, publishes both canonical transfer-amplification gauges atomically, and stops before repository access if received bytes are strictly above both four times changed bytes and one GiB. Missing, duplicated, malformed, or oversized statistics also fail closed. It never takes the whole-VM lock; it waits at most 120 seconds for its dedicated repository lock and exits with temporary-failure status 75 when contention remains. A skipped archive must never appear as a successful systemd run. Each completed attempt atomically publishes only its aggregate success and completion time for node_exporter, while actual canonical-ID verification publishes a separate repository-isolation value.
- The controller's `maintain` subcommand owns retention for only the dedicated PostgreSQL repository. Its systemd unit first requires a fresh successful archive, then runs a bounded partial structure check, preserves every archive within 48 hours before 35 daily and 12 monthly tiers, lists only canonical `loyalty-postgres-*` names to prove the post-prune maximum interval, and compacts only when the interval is at most 300 seconds. Local maintenance contention is capped at 10 seconds, every Borg operation at 15 seconds, and the complete unit at 105 seconds plus a 10-second safe-interrupt window. Its aggregate completion, attempt, recent-count, and maximum-interval metrics use atomic node_exporter textfile replacement. A timeout or malformed, duplicate, future, missing, or over-bound recovery timeline fails visibly; it never continues to compaction. The former `starfiniti-loyalty-postgres-borg` and `starfiniti-loyalty-postgres-borg-maintain` programs remain in the release only as explicitly retained rollback evidence; neither reviewed systemd unit executes them. Never replace the controller with `--content-from-command`: Borg cannot skip unchanged bytes inside one stdin stream, so every run would retransmit the complete backup set from the database VM.

Keep the pull identity restricted to that exact forced command with PTY, forwarding, and user-supplied command execution disabled. Install the matching owner-only rule from `sudoers/`; it permits privilege only through the wrapper, whose root invocation still terminates in `rrsync -ro`. Install both reviewed Borg services/timers from `systemd/`; their isolated cache/security state and the incremental stage are the only supported paths. Configure node-exporter's textfile collector for `/var/lib/node_exporter/textfile_collector`, verify all nine `starfiniti_postgres_*borg*`/off-site and `starfiniti_backup_cycle_*` series are present, and load the exact alert/dashboard assets before enabling production claims. The metric files are world-readable aggregate telemetry by design; their state files remain owner-only and neither surface contains repository IDs, paths, archive names, or credentials.

Provisioning the dedicated repository and the rsync security baseline are explicit recovery changes, not automatic script side effects. Before installing either script, acquire provenance-checked rsync 3.5.0-or-newer packages or builds for both Debian host and Ubuntu guest, record package/source origin, signature/checksum, executable digests, exact rollback packages, both `rsync --version` results, and the guest confinement capability outside Git. The 2026-08-28 live versions—host 3.4.1 and guest 3.2.7—must fail the candidate; do not weaken or bypass the gate to retain a green timer. Create the repository with reviewed encryption, export/escrow its recovery material separately, add `STARFINITI_POSTGRES_BORG_REPO`, `STARFINITI_WHOLE_VM_BORG_REPOSITORY_ID`, and `STARFINITI_POSTGRES_BORG_REPOSITORY_ID` to the root-owned `0400` or `0600` canonical regular non-symlink configuration inside a root-owned non-group/other-writable directory, and prove both repository selectors and canonical 64-hex IDs differ before installing the candidate. Preserve the prior shared-repository PostgreSQL archives. Disable the legacy `starfiniti-loyalty-postgres-borg-prune.timer`; the replacement maintenance unit also conflicts with that legacy service/timer so two retention policies cannot run together. With both new timers still disabled, require restricted-command negative tests, one read-only transport canary, one manual create, exact list/ID comparison, dry-run extract, retention dry run, and isolated restore. Hold the whole-VM lock while creating another PostgreSQL archive to prove isolation; hold the dedicated lock and require both candidate commands to exit 75 without a Borg call. Trigger maintenance through its systemd unit—not the script directly—so its required fresh-archive dependency and whole-service deadline are exercised. Only then enable the three-minute archive timer and daily maintenance timer.

Seed a new stage from a verified archive or one controlled initial pull, then measure guest-interface bytes for a manual run and a timer run. Steady-state transfer must track only newly completed base/WAL files, not the logical size of the full set. Exercise the transfer guard only with mock or synthetic numeric statistics: exact four-times and exact one-GiB fixtures continue, while a cycle above both boundaries retains aggregate evidence and invokes neither Borg identity lookup nor create. Treat status 75 or timeout status 124 as a failed archive/maintenance attempt, investigate the exact dedicated lock owner or slow operation, and measure archive age; the timer's next retry does not erase the gap. After every script change, run `npm run deployment:validate`, create a fresh verified base, force a WAL switch during an incremental pull, and require both a manual and a timer-triggered encrypted off-host archive to finish with exit code zero before applying a production migration. After bounded maintenance, prove its anchor archive, every archive inside the 48-hour window, and the maximum observed archive interval; then run a dry-run extract of the latest archive. Complete repository/index and cryptographic checks remain separate supervised recovery gates. Never delete WAL by age alone: a retained base backup defines the oldest safe cleanup boundary.

If the Supabase database container is recreated, recreate Supavisor after PostgreSQL is healthy so it resolves the current private `db` container address before application traffic resumes. A normal host boot starts both projects from stable service names; this extra step applies to an in-place database-container recreation.

Current breaking changes reviewed 2026-08-11: Envoy is the self-hosted default gateway; `API_EXTERNAL_URL` includes `/auth/v1` in current stacks. Do not apply old Kong-specific examples without an ADR.
