# Threat Model

## Scope and assets

This model covers the public edge, Next.js/BFF, WooCommerce plugin, Supabase Auth/PostgREST/Storage, application/worker database access, PostgreSQL, queues, backups, support tooling, and deployment supply chain.

Highest-value assets are tenant isolation, Auth sessions, customer identifiers, WooCommerce/signing credentials, programme versions, wallet/ledger integrity, coupon/reservation capability, audit history, backups, and availability of checkout-independent connector processing.

## Actors

- unauthenticated internet attacker;
- authenticated customer or merchant attempting privilege escalation;
- compromised WordPress site/plugin credential;
- malicious or mistaken tenant administrator/support operator;
- compromised application/worker container;
- supply-chain attacker;
- infrastructure administrator or stolen backup holder;
- ordinary component failure producing duplicate, delayed, or lost work.

## Trust boundaries

1. Browser/WordPress to public TLS edge.
2. Edge to application and Supabase gateways.
3. Authenticated user context to tenant authorization rows.
4. Application/worker roles to private database commands.
5. Postgres primary storage to backup/off-host storage.
6. Hub outbox to WooCommerce command execution.
7. Support/operator access to tenant-restricted data and actions.

## Abuse cases

- A merchant changes `organization_id` in a request: database composite keys and RLS reject it even if application validation fails.
- A WordPress attacker replays a valid signed body: the delivery ID/nonce and effect uniqueness return the prior result.
- Two checkout sessions reserve the same available points: one transaction obtains the wallet/lot locks; the other sees the committed remaining balance and fails or reserves a smaller valid amount.
- An admin tries to update a published programme or ledger row: no direct DML grant and immutability guards reject it.
- A worker times out after coupon creation: retry uses the same command ID and obtains the existing coupon result.
- A deleted Auth user presents an unexpired token: membership/customer-link checks still fail after revocation.
- A support user changes JWT metadata to enter a tenant: there is no metadata authorization path; a live scoped support grant is required.
- A customer replays or shares an export URL: the route also requires the same verified Auth subject and Supabase session, while PostgreSQL consumes the hashed capability once and rejects expiry or reuse.

## Security requirements by boundary

### Public edge

TLS 1.2+, HSTS after validation, bounded body/header sizes, timeouts, safe forwarded headers, per-IP/connection rate limits, request IDs, and no direct Postgres/Studio exposure. Envoy admin is private.

### Application

Schema validation, origin/CSRF controls for cookie-authenticated mutations, verified Supabase sessions, server-derived actor/tenant context, parameterized database calls, strict response minimization, and no secret-bearing `NEXT_PUBLIC_` variables.

The Next.js request proxy refreshes Supabase Auth through `getAll`/`setAll`, applies the Auth library's private/no-store response headers, and uses `getClaims()` rather than trusting cookie-loaded session objects. It excludes signed WooCommerce API routes from merchant redirects. Server pages verify claims again, query only with the publishable key and user JWT, and derive tenant scope from live membership rows under RLS. Redirect targets must be local absolute application paths.

The workforce callback accepts no legacy PKCE fallback. A valid bounded flow ID and its exact per-flow verifier cookie must both exist before the Supabase client is created or an authorization code is exchanged; missing, malformed, or mismatched correlation fails closed without consuming another pending flow. Every server client and callback derives verifier slots from the same explicit hostname-independent storage key, so an alternate Supabase API hostname cannot silently split PKCE write and read authority.

Customer linking is a separate capability boundary. WooCommerce generates the signed claim locally with its encrypted connector key and performs no render-time hub request. The claim binds connection, numeric customer, issue time, UUID nonce, and current key version; Next.js verifies the HMAC and live connection, requires an existing verified Auth session plus explicit confirmation, sends only proof/nonce hashes to a private runtime command, and applies private/no-store plus no-referrer handling. PostgreSQL serializes the Auth subject and channel identity, consumes each proof once, rejects user/customer conflicts, and appends immutable evidence without email, raw nonce, or signature. Customer self reads accept no selectors and derive the active link from the request subject.

Customer redemption is a distinct value-changing boundary. The confirmation route accepts only a linked account public ID, published reward code, and request UUID after a verified Auth session; PostgreSQL derives the active link, customer, organization, connection, workspace, programme group, published version, and wallet under fixed locks. It independently validates the allowlisted native coupon configuration, reserves points through the immutable FIFO ledger, records the reservation transition, and queues one private customer-bound WooCommerce issue command in the same transaction. The response contains only reservation identity/state/outcome. Exact retries return the original result, changed request reuse conflicts, and any failure rolls back every effect; definitive issue failure or confirmed-unused expiry later releases points through compensation rather than history edits.

Customer export is a separate read capability rather than an extension of the bounded account projection. The customer must enter their password again; the runtime verifies the resulting Auth claims, issues a random five-minute capability, and binds it to that Auth subject and session. The download route supplies only that private capability plus the verified subject/session to one transaction. PostgreSQL consumes the stored digest once, rechecks all active customer, link, workspace, connection, and programme scope, creates payload-free immutable audit evidence, and returns the complete versioned document. The runtime adds the verified Auth email and sends the JSON directly with defensive private download headers; neither layer persists document content.

Connector provisioning is a server-only secret distribution boundary. The browser submits public workspace/programme identifiers and bounded store/display inputs after verified Auth; it cannot select a credential reference or call the private PostgreSQL function. The runtime chooses an unused reference from the root-readable, read-only mounted pool, while PostgreSQL rechecks live owner/admin membership, active workspace/programme linkage, published state, idempotency, and global reference uniqueness. The exact endpoint/connection/version/key package is returned only in the successful server-action result for immediate transfer to WordPress. Neither the browser Data API nor immutable audit metadata exposes the reference, and the plugin validates the exact package before encrypting the key with Sodium-backed storage.

WooCommerce customer erasure enters only through the verified signed commerce path and a strict payload containing the numeric source ID without contact/profile data. The local idempotency key and source object are opaque. The leased worker command binds the canonical event to its tenant, connection, worker, source kind, and exact payload; it HMACs the low-entropy subject with separately stored random connection material, appends an immutable private case, pseudonymizes the channel/customer display state, revokes hosted links, and scrubs raw/canonical event identifiers atomically. Missing identities still create suppression tombstones, while wallets and immutable ledger evidence are never deleted or adjusted.

Merchant programme mutations omit actor and organization IDs from their public contracts. Exact-signature Data API wrappers derive the actor from request claims, recheck live owner/admin membership, canonicalize and hash persisted JSON in PostgreSQL, and append immutable tenant audit evidence in the same transaction. Exact idempotency retries return the original result; changed input, stale hashes, revoked roles, and cross-tenant resource IDs fail closed.

Initial programme onboarding uses the same command boundary: the browser supplies only an active programme-group public ID plus validated display inputs and command identity. PostgreSQL locks and resolves the group, derives its organization, rechecks the request actor's live owner/admin role, inserts the programme, and commits immutable audit evidence atomically. Authenticated clients retain no direct programme insert grant, and public tenant signup/provisioning stays disabled.

Enterprise access review is a separate minimized read boundary. The browser supplies one public organization selector, while PostgreSQL derives the Auth subject, live membership, assigned role, active organization state, catalogue permissions, and aggregate role counts. Email, domain, upstream OIDC/SAML groups, JWT role/organization metadata, Auth UUIDs, tokens, secrets, and individual member identities never enter the result. The immutable Access V1 catalogue contains six membership roles and one structurally grant-only support profile. Revocation fails on the next database request even if an access JWT remains valid; organization suspension leaves the review evidence visible but makes the assigned profile explicitly ineffective. The catalogue governs only M13 administration and does not silently broaden legacy loyalty command roles.

Organization and team lifecycle is a separate command boundary. A new organization derives the current Auth subject and atomically creates its first owner. Invitations are 256-bit one-use capabilities; only a SHA-256 digest crosses into persistent storage, and acceptance derives the current Auth subject rather than accepting an email, user, tenant, domain, or group. Owner/admin mutations require exact role/state/revision contracts, reason, and confirmation. Every mutation locks the stable organization row and rechecks the actor after that lock, preventing stale authority and reciprocal owner-removal races. Closing is irreversible; offboarding preserves one owner and all immutable value/audit/export evidence while revoking non-owners and pending invitations. The minimized team projection exposes bounded labels, roles, lifecycle revisions, capability-free invitation status, and audit summaries only to an owner, live admin, or live auditor. The boundary has no ledger privilege or effect.

Merchant customer reads enter exact-signature stable wrappers that validate public UUIDs, recheck live membership, apply literal bounded reference search and fixed result ceilings, and mask external channel identifiers before they leave PostgreSQL. Wallet and ledger bigints cross the Data API as text. The customer timeline exposes wallet-side ledger evidence and correlation context but omits raw commerce payloads, ledger metadata/reasons/request hashes, actor IDs, contact attributes, and unrelated identities.

Outbound webhook lifecycle mutations use exact-signature authenticated wrappers that derive the actor from PostgreSQL request claims and derive the organization from an active workspace or endpoint. They accept no actor, organization, or tenant input. The private primitives are not executable by browser, runtime, or worker roles, so a trusted server bridge cannot substitute actor authority. Creation and rotation receive only a one-way secret fingerprint and bounded hint; raw signing material remains confined to the one-time server response and isolated worker mount.

Customer tier visibility is a separate one-row wrapper over the current membership interval and its immutable decision. It exposes current/qualified labels, transition, exact eligible-spend minor units, and timing only; internal explanations, command identities, request hashes, actors, and unrelated history remain inaccessible. Active tenant/group and live membership checks fail closed for revoked, suspended, mismatched, and cross-tenant requests.

Merchant connector reads enter exact-signature security-definer wrappers because queue tables are private. The wrappers recheck live tenant membership and return only bounded state, count, attempt, error-code, event/topic, and watermark fields. They never return queue payloads, raw bodies, source object identifiers, coupon codes, signing references, or customer attributes. Effect replay is restricted to live owner/admin/operator roles, dead-letter canonical effects, a bounded reason, and immutable audit evidence. Quarantined work and compensated coupon commands cannot be replayed through this surface.

The merchant-generated support bundle has a second allowlist boundary over those reads. It exports public tenant/connection scope, queue totals, watermarks, and a labelled bounded sample of grouped canonical codes only; individual operation IDs, names, actors, reasons, payloads, commerce/customer identifiers, signing references, and noncanonical text are removed before browser download. It grants no support access and does not bypass live tenant authorization.

Source-order reconciliation is a separate narrow command, not a generic outbox replay. PostgreSQL derives the actor, rechecks owner/admin/operator membership and live connection status, validates one canonical numeric order ID and bounded reason, and atomically records audit evidence with a private signed outbox command. The plugin re-emits WooCommerce source facts through existing source-revision and central idempotency fences; it cannot directly mutate the ledger. Missing orders dead-letter rather than creating a retry storm.

Overview analytics enter one exact-signature stable wrapper that rechecks live membership and the active organization/workspace/programme relationship. Date ranges are allowlisted and aligned in UTC. Private evaluations, canonical payloads, identities, ledger entries, actors, and reasons remain inaccessible to browser roles; only minimized exact aggregates and bounded daily counts are returned. The UI uses text-form integers and `BigInt`, states metric definitions, and shows no illustrative fallback that could be mistaken for tenant truth.

Manual point adjustment is treated as a high-risk value command. The public contract omits actor/organization IDs, preserves point values as integer strings, requires deliberate review and a bounded reason, and gives removal a distinct warning/confirmation. PostgreSQL rechecks live owner/admin membership, customer/group/version relationships, and expiry direction before invoking the immutable ledger primitive. Operators, analysts, auditors, revoked users, stale versions, and cross-tenant targets fail closed. The ledger and administration audit rows are committed together and cannot be rewritten.

Customer-experience theming uses a data-only boundary. The public contract and PostgreSQL independently allow one canonical accessible brand color, an allowlisted local font stack, three radii, bounded customer copy, two visibility flags, and widget side. The command derives linked workspace/programme-group scope and actor from live tenant state, permits only owner/admin, serializes revisions, and appends immutable audit evidence. It accepts no CSS, script, HTML, URL, upload, organization ID, or actor ID; other roles, revoked users, unlinked scope, idempotency conflicts, and cross-tenant IDs fail closed.

## Residual risk and gate result

All critical threats have a concrete preventive/detective control and executable verification assigned to a build phase. None requires an unresolved product decision. The controls are not yet all implemented, so production readiness remains an automatic fail; Phase 2's design gate passes only after these documents and ADRs are reviewed by CI/diff evidence.

## Service-account bearer and namespace threats

- **Credential disclosure:** a 256-bit token is returned once and stored only as a SHA-256 digest plus six-character hint. Management reads, audit, logs, support bundles, browser hydration, and errors exclude it. HTTPS and a sender-side secret manager are mandatory; compromise is contained by immediate database revocation.
- **Selector or tenant substitution:** the request carries only the token-derived public credential selector and strict activity/customer fields. PostgreSQL resolves and locks credential, organization, account, workspace, programme, connection, entitlement, scope, customer, and quota. A public UUID is never authority by itself.
- **Cross-customer or email merge:** raw external references are HMACed under one private random account pepper. Namespace uniqueness is database-enforced and email/domain/profile attributes are neither accepted nor queried.
- **Replay and changed reuse:** immutable request hashes, account-scoped idempotency constraints, canonical source event identity, and existing effect receipts return exact duplicates and reject content drift.
- **Rotation race, expired key, or quota overshoot:** credential/account locks make lifecycle checks and fixed-window increments atomic. Two-session probes cover customer creation and concurrent quota consumers; revocation fails on the next request.
- **Alternative value path:** activity acceptance writes only the canonical commerce ingress. Programme evaluation, caps, worker authorization, effect receipts, and immutable ledger transactions remain authoritative. Service API/entitlement failure cannot affect checkout, refunds, reconciliation, or existing balances.

The existing Merchant Activity HMAC boundary remains purpose-separated and compatible. Its key cannot authenticate a Service API request, and a Service API bearer cannot authenticate WooCommerce or Merchant Activity delivery.
