## M14-S05B managed growth/configuration enforcement

- ADR-0061 selects table-bound commercial guards over a global entitlement substitution or UI-only restriction. A private immutable inventory maps 23 reviewed mutable growth/configuration roots to their product capability, lifecycle column, commercially safe states, and command family; exactly one ordered `BEFORE` guard trigger is installed on each root.
- Commercial and product authority stay separate. Existing commands and validators remain authoritative for `programme.v2`, campaigns, rewards, referrals, notifications, analytics, ecosystem, migration, and enterprise administration; the new guard evaluates only effective tenant-canary `managed.billing` policy. This preserves mixed immutable V1/V2 history and avoids treating the table root as proof of one product contract.
- Commercial enforcement is off unless the organization is managed and its exact tenant canary has effective `managed.billing`. Self-hosted installations pass locally with no Stripe or remote entitlement dependency. Managed tenants in trial, active, grace, or effective contract-managed states may create configuration; unconfigured, suspended, or cancelled tenants may not.
- Safe risk-reducing lifecycle changes remain available while restricted: campaign pause/cancel, endpoint disable/retire, report-schedule pause, credential revocation, return to isolated sharing, currency-policy disablement, and federation validation/disable/retire/recovery completion. Ledger, wallet, lot, reservation, commerce event, customer link, export, organization-access, correction, and checkout roots are structurally absent from the guard inventory.
- Database role—not request JWT role or metadata—controls privileged recovery bypass. `postgres`, `loyalty_owner`, and `loyalty_worker` stay independent from stale request claims; `loyalty_runtime` remains commercially evaluated and retains subjectless access only through existing private merchant functions that separately validate their explicit actor. Authenticated or unknown subjectless callers fail closed.
- Exact immutable retries stay readable while restricted because their command fences resolve before new DML. The twenty-second two-session probe proves concurrent exact authoring creates one effect, its historical retry remains readable after restriction, changed growth fails closed, active recovery reopens configuration, and no loyalty ledger value changes.
