## M14-S02 verified webhook inbox and isolated normalization

- ADR-0057 selects exact in-memory HMAC verification plus an immutable minimized receipt and independently leased normalization job. Synchronous lifecycle processing, raw provider-event storage, and construction of a broad Stripe provider client solely for HMAC were rejected.
- The route calls the PostgreSQL deployment/entitlement gate before body or secret access. It then enforces JSON media type, a 256 KiB streamed ceiling, exact `{timestamp}.{raw-body}` HMAC-SHA256, constant-time comparison, one to eight `v1` rotation signatures, and a five-minute tolerance.
- The strict internal contract reconstructs only allowlisted subscription/invoice evidence. Raw bodies, signature headers, contact, metadata, invoice bodies, payment instruments, cards, secrets, and provider responses are absent from schema, logs, worker inputs, and public responses.
- PostgreSQL derives tenant authority from one current private account plus its stable-subject `managed.billing` entitlement. Exact Stripe event retries return one receipt; body or lifecycle drift under the same event ID fails. Entitlement is rechecked at intake, claim, and effect.
- The optional `billing` worker profile has only `loyalty_worker` database authority and no Stripe secret, API key, SDK client, or provider network action. Subscription events append through the S01 event-time boundary; invoice events are immutable observations only. Leases are bounded, recover after expiry, cap at ten attempts, and append immutable outcomes.

## M14-S03 database-reserved Checkout and Portal sessions

- ADR-0058 selects database reservation and reauthorization before a narrow direct Stripe REST adapter. Browser-created sessions, a broad provider SDK, provider-return authority, and live Stripe subscription authorization were rejected.
- Strict V1 contracts accept only public organization/plan selectors, an action, and an operation ID. Public plan output contains reviewed display, amount, interval, and trial fields; provider customers, Price IDs, API keys, returns, and commercial authority remain private.
- Additive private RLS tables retain immutable provider configuration, exact plan versions, operation fences, and minimized provider attempts. PostgreSQL derives a live owner, active tenant, `managed.billing` entitlement, effective plan/Price, provider mode, account, and stable idempotency key before each external request.
- Initial provider-customer creation is serialized per organization. Exact reservation and customer-result retries converge; changed retries fail closed; ambiguous outcomes retain their fences; historical operations keep their exact Price evidence after a later plan version disables new selection.
- Entitlement or provider disablement commits a recoverable `held` state and returns no provider authority. The dashboard reads no API-key file and constructs no client when authorization returns no row. Self-hosted mode returns even earlier, before tenant, plan, account, provider configuration, key, or client access.
- The Stripe boundary accepts secret or restricted keys from an absolute regular file, fixes production to `https://api.stripe.com`, pins API version `2026-02-25.clover`, sends POST only, follows no redirects, bounds time and response bytes, and returns only validated official Checkout or Billing Portal URLs. It stores no redirect, response, contact, payment, card, body, or secret material.
- The responsive Billing route adds owner-only plan and portal controls to the existing Hub shell. Checkout success/cancel and Portal returns are navigation only; only the separately verified S02 webhook path can append commercial lifecycle evidence.
- The first Linux database run exposed three assertion-fixture mistakes and one real transactional flaw: raising after setting a hold rolled that hold back. The corrected function commits the hold and returns zero authority; the server regression proves no key or provider access follows.
